# Support360 implementation status

Last reviewed: 2026-11-12

This status reflects code present in the repository and commands run in this workspace. A checked-in file alone does not count as a verified feature.

## Repository inspected

- `src/`: ASP.NET Core .NET 10 modular monolith split into API, Application, Contracts, Domain, Infrastructure, and Workers projects.
- `src/Support360.Infrastructure/Persistence`: EF Core PostgreSQL migration, SQLite development provider, tenant query filters, persistence write guard, and demo seeder.
- `tests/`: xUnit unit and API integration projects.
- `web/`: React 19, TypeScript, Vite administrative UI with REST client and SignalR reconnect hook.
- `src/Support360.Agent`: .NET 10 (C#) monitoring agent with enrollment, authenticated telemetry, bounded persistent telemetry and application-result queues, platform-specific check code, signed-manifest deployment verification and ZIP installation, unit tests in `tests/Support360.Tests.Agent`, Windows service and Linux systemd packaging. Native installers and runtime OS verification are incomplete.
- Docker Compose, GitHub Actions, root operator guide, architecture notes, and initial threat model are present.

## Phase plan and acceptance criteria

1. **Foundation (implemented for local development):** reproducible PostgreSQL/API/web stack; environment template has placeholders; CI runs .NET, PostgreSQL integration, and frontend build; architecture, threat model, and status docs reflect current scope.
2. **Monitoring agent MVP (partially implemented):** .NET (C#) agent enrollment, authenticated heartbeat/telemetry, bounded persistent telemetry/check-result queues, real host metrics, and HTTP/process/Windows service/Linux systemd checks. Native OS installation/runtime verification remains.
3. **Operational monitoring (partially implemented):** application check configuration, editing, result history, batch-job events, alert lifecycle, dashboards, and live updates. Role-policy, cross-tenant, and incident/change frontend interaction coverage was added; wider lifecycle and authentication UI coverage remains.
4. **Controlled deployment (implemented, disabled by default):** approval enforcement, RSA-PSS signed target-bound manifests, nonce replay protection, digest-verified artifact download, deployment-root allowlisting, agent-side installation, result reporting, and audit are present. Production key management, health verification, and failure-recovery acceptance tests remain.
5. **Production readiness:** tenant-isolation/security review, operational runbooks, retention and recovery validation, signed releases, and supported-platform install/upgrade verification.

Operators stage a request bound to an active same-tenant agent, immutable package name/version/digest, target path, and a same-tenant change request; change approval synchronizes the request status. Execution requires the server gate, a configured RSA signing key, the tenant administrator grant, and the local agent opt-in. ## Known blockers and next steps

- Verify the configurable OIDC claim mapping against an external identity provider and run the authorization matrix against PostgreSQL.
- Add per-tenant HTTP check target allowlists or an egress policy and review cloud metadata/IPv6/DNS-rebinding risks; scheme/credential validation, redirect blocking, proxy isolation, and timeouts are now enforced by API and agent. Agent-scoped telemetry, job-result, credential-rotation, and suspended-tenant authorization coverage is in place.
- Verify Windows service install/start/stop and identity ACLs on Windows Server; execute systemd install/upgrade/uninstall on explicitly supported Linux distributions.
- Verify the incident/change/deployment interaction tests against the live API; authentication/session UI coverage (login, expiry, route guarding, role-based navigation, sign-out) is now in place.
- Add scheduler-specific adapters or missed-run evaluation only when supported schedule semantics and scheduler integrations are defined; current schedule text is descriptive.
- Exercise signed deployment execution end to end with a live agent (including failed download, tampered artifact, expired/replayed manifest, and rollback recovery) before enabling `Deployment:ExecutionEnabled` outside test environments. Define signing-key generation, distribution, rotation, and revocation procedures; keep the private key out of source control.
- Run the agent and API together for a live manifest/artifact/result deployment smoke test now that `AddDeploymentManifestNonces` is applied; this still requires enabling deployment execution and configuring a signing key pair.
- Replace PostgreSQL package BLOB storage with a durable artifact-store implementation before production or larger packages; consider package-signing trust in addition to the manifest signature.
- Extend Work DNA with agent diagnostic auto-capture, automatic `OFF`-day activity suppression (beyond per-activity `Ignore OFF`), capacity views across multiple months, and CI/CD governance gates when those source systems are defined.
